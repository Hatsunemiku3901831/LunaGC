## 保存顺序

1. 保存 `kind=recipe` 的原计划：操作 UUID、原书实例 ID、原数量、学习操作与目标；乐谱同时记录自己的家园 ID。
2. 确认扣除原实例的一本书。`recipeUseOperationId` 与数量、删除状态、物品版本写在同一次条件更新中，
   不能仅凭剩余数量认定已经扣费。
3. 保存对应玩家或家园的解锁集合，再确认完成阶段并清除计划。
4. 使用原来的配方、家具或乐谱通知消息同步客户端。显示通知失败后保留已确认结果，避免再次扣书。

新取得但尚未保存的书先确认原数量；家园首次保存先取得稳定 ID。
最后一本书保留[删除凭证](ITEM_SAVE_FENCE_2026-10-17.md)。
扣费凭证也会随以后补书、继续消耗和删除保留；不会把另一堆新书当作原成本再次扣除。
食谱恢复使用已有条目时保留后续熟练度。

## GM 与控制台

| 命令 | 用途 |
| --- | --- |
| `itemuse @10001 status` | 只读查看原计划、当前数量与扣费凭证 |
| `itemuse @10001 resume <operationId>` | 核对原计划，继续尚未完成的学习；已确认成本不再扣除 |
| `itemuse @10001 cancel <operationId>` | 仅取消尚未扣费且尚未解锁的预留 |

权限继续使用 `server.itemuse` 和 `server.itemuse.others`。目标玩家需要有与存档一致的当前库存；
若提示内存不一致，应重新登录后核对。

取消会先更新原物品版本，使晚到的旧扣费失效。已付费的学习只能继续，不会借用食物退款入口发回一本书。
目标、资源、归属或持久 ID 不符时保留计划；缺少扣费凭证时不会用数量猜测结果。
资源变化不能把旧计划转向另一个目标，未扣费的旧计划仍可安全取消。

食物仍使用原来的 `refund-cost`／`settle`；其他礼包和物品效果继续按各自的实现范围处理。

本轮未使用实际玩家数据库进行这些测试，没有启动游戏。
这套计划不代表所有库存、货币、家园整份文档或多进程业务已经具有完整事务隔离。
直接解锁／取得时使用等其他入口，以及实际游戏画面，仍按各自验证范围核对。
旧构建不认识新的学习计划和扣费标记，不能用它处理尚未结束的新学习记录。
