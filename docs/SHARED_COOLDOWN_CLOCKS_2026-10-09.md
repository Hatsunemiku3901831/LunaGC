# 玩家时间与实时共享冷却：2026-10-09

## 对上一批的纠正

第六十三批的协议、资源关联、槽位和串行次数恢复继续使用，但其场景时间假设不正确。
客户端普通共享冷却使用玩家时间，另一类使用同步后的服务器时间。场景时间不能作为
这两个时钟的替代；上一批关于换场景清空和无符号场景时间的测试只验证了当时的实现，
没有证明客户端采用该基准。本批纠正实现与检查，替换上一批候选运行包。

- 会话持有独立的玩家时间，从零开始，以单调时间计算毫秒。普通冷却和
  `PlayerTimeNotify.player_time` 使用同一来源，暂停时冻结，恢复时排除暂停的间隔。
  时间与暂停标记在同一快照中读取；暂停状态改变时向客户端同步。
- `PingReq.client_time` 继续用于原有网络回声和连接状态，不再作为玩家时间。
  因而两次心跳之间冷却仍能推进，网络样本回退或跨过整数边界不会改变冷却。
  这也避免把有符号整数直接写进 `uint64 player_time`。
- `isUseRealTime` 组使用与 `server_time` 一致的 Unix 毫秒，暂停玩家时间不会阻止
  这类组恢复。服务器时间调整后，已有 Unix 时间端点继续按调整后的时间判断到期。
- 换场景和场景传送期间保留当前玩家的队列；不能在脱离场景时开始或清空冷却。
  进入场景导入剩余队列。会话更换清空旧会话状态；玩家时间回退只清空普通时间组，
  不把实时组当作同一个时钟重置。条件、所属玩家、实体生命周期和次数限制继续检查。
- 饱食度通知的结束时间改用相同玩家时间，避免通知一套基准、结束时间另一套基准。
  本批没有改变饱食度本身的减少规则。

实际资源中的活动技能 20109 使用实时组 20081、300 秒冷却，现可接入。
73 个共享动作节点中 72 个通过检查；20116 没有共享组，其普通冷却未由本模块代替。
这不代表上述活动的任务、解锁、父状态和实机流程全部完成。

| 代码位置 | 观察到的行为 |
| --- | --- |
| `0x14c838f80` | 按共享组 `isUseRealTime` 选择两套 getter |
| `0x14ef8ca30` | 当前 DateTime 加服务器偏移，再减纪元 |

| `0x14ef8f590` | 构造 1970-01-01 UTC，再转本地 DateTime 作为纪元 |
| `0x14ef88290` | 更新玩家偏移、暂停标记和冻结值 |
| `0x14ef8e310` | 以毫秒输入更新服务器偏移 |
| `0x14c255d90` | 从通知的两项时间和暂停标记更新上述两个时钟 |

两套 getter 把 DateTime tick 差乘 `0.0001`，因此输出单位是毫秒。
服务器和玩家偏移存储分别为 `0x145789328`、`0x145789320`；
暂停标记和冻结值分别为 `0x1457892a3`、`0x1457892b8`。
通知消费路径还根据包头时间计算传输延迟，暂停时不把该延迟加入玩家时间。

包号 20114 的类型 `KNHBIEFHDFO`（55958）读取函数 `0x149c0b160` 核实
字段 7 为玩家 `uint64`、字段 6 为服务器 `uint64`、字段 15 为暂停 `bool`。
消费路径读取对应实例偏移 `0x18`、`0x20`、`0x28`。共享通知的三层字段、
槽位含义和次数队列证据保持上一批结果；完整同步标记的所有消费者没有逐一恢复。
