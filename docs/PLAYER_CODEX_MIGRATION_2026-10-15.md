# 玩家读档与图鉴迁移的保存边界

上一轮经济恢复回归发现，完整查询玩家时会经过
`Player.onLoad -> PlayerCodex.setPlayer -> fixReliquaries -> Player.save`。
参考 AstaPS 固定提交 `7cc148d1f752a43d4b9146b3b73f26875902546f` 也保留类似的图鉴保存调用。
每次查询都给独立玩家副本排队保存，可能晚于在线玩家的新状态写入，造成进度回滚。

## 修复

- `PlayerCodex.setPlayer` 绑定持有者，并在内存中兼容旧图鉴格式；不保存玩家，也不发送图鉴通知。
- 保留圣遗物编号归一化：多个初始副词条形式合并为对应的零副词条编号。
  依据当前资源补全已经集齐的套装图鉴；未集齐全部资源部位时不补全。
- 用不进入存档的迁移标记记住内存变化，重复绑定不会丢失该标记。
- `Player.onLogin` 开头调用图鉴迁移确认，在世界管理器启动前保存需要迁移的实际登录玩家。
  使用带确认的同步保存，保存成功才清除标记；提交前失败和提交后确认失败均可重试。
- 登录时重新检查当前资源，覆盖读档后新载入的套装定义。
  空图鉴和已经完整归一化的图鉴不额外保存。
- 兼容空缺图鉴、空集合和圣遗物集合中的 null 条目；有效的书籍、武器等其他收藏保留。
  显式保存后的记录可以正常再次读取。默认构造器已经提供的空值不强制触发一次迁移写入。

普通 UID 查询和 Morphia 实体查询现在均可读出兼容后的图鉴，数据库原记录保持不变。
经济核对继续使用已有的字段投影读取。

## 验证

测试使用当前 `ReliquaryCodexExcelConfigData.json` 的真实五部位套装和隔离 Mongo。
初次运行的数据库用例缺少夹具队伍数据；补入正常队伍后，13 项检查全部失败，才进入修复。

除确认查询额外产生一次玩家写入，还用阻塞数据库写入队列固定复现了覆盖顺序：
先查询到进度 1500 的副本，再同步提交进度 4500，最后释放旧副本写入。
修复前数据库退回 1500；修复后仍为 4500。
该检查使用真实查询、真实数据库队列和实际存档值。

实现后首轮 13 项通过，随后加入完整图鉴／空图鉴的零额外保存和重复绑定保留待保存状态检查。
登录入口检查调用真实 `Player.onLogin`，在后续神像管理器启动时中止，
确认该边界之前迁移已经落库；没有据此声称整个客户端登录流程完成。
另覆盖同步保存失败前后两种实际提交状态、资源后载入、未完整套装、
其他收藏保留、迁移标记不进入 BSON，以及旧空值格式的读取与显式保存。

原始证据在 `debug/aster-mid-20261011/batch253/`：
`codex-migration-red.xml`、`codex-migration-red-confirm.xml`、`codex-migration-first.xml` 和对应日志。
