# TPS 射击与换弹上报的确认写入

## 修复

原路径在修改总弹药与弹匣后调用异步 `player.save()`，随后允许转发上报。
保存完成与否没有进入接受条件；失败时，已经修改的内存状态和已转发结果可能缺少持久化依据。

有效的 Cost／Reload 变化现在通过一次确认写入，将两个完整数量映射和 `lastTpsReport`
同时保存到同一个 Player 文档。使用现有 `saveTpsAmmunition()` 的 majority／journal 确认。
确认成功才返回接受结果；无数量变化的上报不写库。
这条高频路径没有为每次射击增加补给计划使用的多阶段写入。

最后一条结果覆盖上一条结果，不追加无限历史。记录包含操作 ID、冻结 UID、前序 ID、
原始上报、场景／角色、原始与最终数量、当时的资源容量。
原始上报保存上限为 1 MiB，这是本实现的记录限制，不是客户端协议范围的推断。

## 确认异常与恢复

确认异常时，在当前活动 Player 对象中保留本次候选结果，暂停新的射击／换弹、
补给、补满、总量变更、换装和 TPS 武器移除。移除检查发生在背包修改前。
其他正常的玩家保存可能保存这个完整候选结果；核对会识别这种情况。

GM 命令仍使用 `tps pending`、`tps audit <operationId>`、`tps resume <operationId>`、
`tps cancel <operationId>`，沿用目标 UID 的选择方式：

- `pending` 同时列出补给和射击／换弹的待处理状态。
- `audit` 只读取原始 BSON 投影，不重新解码 Player，也不写回存档。
- 存档仍为完整旧状态时，`resume` 确认保存原冻结结果，`cancel` 恢复原数量及上一条结果记录。
- 存档已包含完整新结果时，`resume` 直接确认，不再写入或再次扣弹；`cancel` 被拒绝。
- UID、前序记录、总量、弹匣或当前候选状态不符时，拒绝覆盖。
- 恢复发送绝对总量和现有武器的弹匣快照，不重放消耗增量，不重建武器实体。
  失效、被替换的角色以及跨世界状态不会重新发布旧装备。

未确认尝试属于当前活动对象；存档本身只会有旧完整状态或新完整结果。
进程重启后，未落盘且未被接受的尝试不成为持久待办；已经落盘的结果可由新 Player 正常冷读。
现有近期、带时钟的完全相同上报去重仍生效；没有把客户端时钟或内部操作 ID 当作跨会话全局 nonce。

后续已补齐[恢复决定与存档版本之间的核对](TPS_RECOVERY_SAVE_FENCE_2026-10-16.md)：
`resume`／`cancel` 先识别或阻止未确认写入，再按本对象确认的版本读取业务结果。
已经落库的晚到结果也会拒绝取消；`audit` 保持只读。
