# 活动存档的版本保护

## 问题与处理

活动余额、任务进度和领奖记录保存在同一份 `activities` 文档中。此前同步保存和排队保存都会
直接替换整份文档：两份对象读取同一旧档后，较晚保存的旧对象可以覆盖另一份对象已经确认的余额，
甚至将新复刻的排期改回旧排期。

本次将项目已有的 Player 保存版本保护策略适配到活动文档：

- 每次确认保存生成递增版本和独立写入令牌。替换时同时核对文档 ID、UID、活动、原排期和原版本。
- 同步保存、异步队列和通用保存入口使用同一保护；重复 ID 不再退回无条件替换。
- 新对象只能插入，不能凭相同 ID 覆盖现有存档。已经加载的旧对象不能重新创建已删除的存档。
- 旧档没有版本字段时，读取不迁移、不排队；第一次明确保存才添加版本。两个旧档读取者只能有一个成功。
- 同一个活动对象的排队保存可以使用它最近确认的版本；另一份冷读对象不能借此采用别人的版本。
- 读取或首次写入后固定保存目标，队列仍使用提交时捕获的数据库；后续换库会拒绝保存。
- 新复刻继承原活动文档已经确认的保存身份，再写入新排期及清空后的数据。未确认写入、冲突或冻结余额会阻止复刻重置。

## 写入应答丢失

操作保留发送时已经编码的文档及写入令牌。下一次保存前先核对结果：

1. 数据库记录的是本次写入令牌时，确认本次结果。
2. 新建文档仍不存在时，重发完全相同的插入文档。
3. 替换尚未发生时，以条件更新只推进保存元数据，阻止延迟的原替换随后覆盖新结果。
4. 其他对象已经提交，或无法读取结果时，拒绝继续覆盖。

元数据更新也可能丢失应答；其独立令牌可以再次核对。条件读取使用主节点、多数读取，
插入、替换和元数据更新使用多数确认及日志写入。活动货币原有的未确认余额冻结仍然保留，
通用保存入口也不能绕过冻结继续写入。

## 验证

证据保存于 `debug/aster-mid-20261011/batch340/`。原实现上先运行 13 项真实 Mongo 回归，
13 项断言失败，0 错误、0 跳过，保留于 `red-results/` 和 `red-business-tests.java`。
加入版本保护后的两套核心用例共 31 项通过；随后继续补充队列、冻结和原排期保护。

旧版 Morphia 的 String ID 映射不接受 BSON ObjectId 类型的活动 ID；相关夹具最初假设兼容两种类型，
首轮因此有一项失败，记录保留于 `initial-green-results/`。用例已分别验证原有 String ID 正常迁移，
不兼容 ID 拒绝读取且不写入，未把它当作可以自动转换的历史格式。

业务回归中的写入故障改为注入实际活动条件写入，仍执行隔离 Mongo 操作；
百货奇货、熄星奖励、原始场景及商店原有的写入前失败／写入后应答丢失断言继续保留。

扩展首轮 30 套、411 项有 12 项失败，集中在冷读故障注入尚未建立存储引用，
以及旧夹具直接建档后没有初始化活动／Player 保存版本。这一轮保留于 `first-final-results/`。
夹具修正后，相同范围 30 套、411 项全部通过，0 失败、0 错误、0 跳过；
其中活动保存保护自身有 34 项真实 Mongo 用例。最终结果见 `final-summary.json`。

## 后续范围

这项保护约束同一活动文档的覆盖，不是完整商店或领奖事务。
付款、背包发货、玩家档案和活动存档之间的操作 ID、持久化预留、核对、恢复及退款仍需继续接入。
新建不同文档 ID 时的 UID／活动唯一归属和历史重复档清理也没有在本次实现。
业务操作跨服务进程的所有权、真实主从切换、网络超时和客户端玩法验收仍然保留。

运行旧版无条件保存程序会绕过新策略，服务切换时需退出旧服务再启动新构建。
本次没有启动游戏，没有更改真实玩家的余额或领奖进度。
