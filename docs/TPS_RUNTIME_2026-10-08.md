## 换装后的能力归属

原来的 `sendEquipChange` 重建武器实体时没有传入穿戴角色。
武器能力在构造实体时就会初始化；此时物品尚未绑定新实体，无法依靠物品指针追溯穿戴者。
这会使新能力使用世界主人的能力管理器，词条也可能没有实际施法角色。

现在换装重建实体时直接绑定角色，初始化能力使用该角色的玩家和管理器。
测试读取真实冰枪模型及能力资源，检查其五个能力，包括普通射击、换弹、冰激光和准备动作。
测试场景的世界主人与穿戴玩家分别创建，能够复现错误地使用世界主人的路径。
再次换装通知仍会清理旧武器，新实体保留实际穿戴者。

## 弹药消息处理和转发

TPS 弹药更新属于能力元消息，但原来非零 `localId` 会先进入普通动作／混合器分发，
无法到达弹药扣除处理。现在按消息类型优先进入 TPS 校验，保留已有的 `onAbilityInvoke` 入口。
四种接包入口通过新增的 `acceptAbilityInvoke` 取得处理结果：

| 接包入口 | 转发队列 |
| --- | --- |
| AbilityInvocationsNotify | 常规能力队列 |
| ClientAbilityChangeNotify | 常规能力队列 |
| ClientAbilityInitFinishNotify | 初始化完成队列 |
| ClientAbilitiesInitFinishCombineNotify | 初始化完成队列 |

原来弹药校验返回拒绝后，接包函数仍把消息加入转发队列。
现在只有接受的 TPS 更新会入队；未知拥有者、客户端自增补给和超额扣除不会再转发给其他玩家。
畸形 TPS protobuf 条目会被跳过，同一批后续合法条目可以继续处理。
其他能力消息沿用原来的处理和转发行为。

扣除时进一步检查实体实际身份：当前角色必须仍在当前场景登记，且属于该玩家；
武器必须是当前穿戴武器、绑定当前角色，并且与场景武器表中的对象一致。
已移除或同 ID 替换的对象、物品残留的旧实体指针不能继续消耗储备。
场景尚未创建时的 TPS 更新直接忽略。

## 资源对比结论

逐一比较能力目录中的混淆字段副本与明文副本，找到 **85 个 TPS 名称、21 个混淆副本文件**，
这些名称都有明文对应项。此前局部扫描中的被跳过行数不能直接解释为缺少同等数量的能力。
比较同时记录了字段值相同、字典键集合相同的证据；没有据此给全部新版嵌套字段增加猜测别名，
也没有让仅解析部分字段的副本覆盖现有明文配置。

参考库对弹匣、换弹、补给通知仍标记为实验或待确认；本批修复消息处理链，
未把参考库的实验开关当作完整玩法。
