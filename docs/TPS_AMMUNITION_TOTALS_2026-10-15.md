# TPS 弹药总量与全量通知

本次继续核对固定 7.1 客户端中的 TPS 运行路径，补齐 `TpsRegionalPlaySupplyInfoNotify`，
并修正进入场景与 `/tps refill` 的同步。既有装备和费用校验见[TPS 运行记录](TPS_RUNTIME_2026-10-08.md)。

## 当前客户端证据

使用[客户端提取工具](../tools/extract_client_type_names.py)相同的二进制／metadata 哈希配置，
按实际 PE 函数范围追踪以下原生分支：

| 类型／入口 | 含义 |
| --- | --- |
| `JONAGHOAMLH`，包号 6579 | 清空原总量表，再用通知中的绝对数量重建 |
| `EBPGOAKBPBG` | 单条总量：config ID 字段 1，uint32 总量字段 14 |
| `JONAGHOAMLH.NLGBJEEJDLG`，`0x151f34b10` | 列表标签 `0x5a`，即字段 11 |
| `EBPGOAKBPBG.NLGBJEEJDLG`，`0x14b0b0c10` | 接受标签 `0x08`／`0x70` |
| `MHKNMCLEABC.NKEGFKKJIFL(JONAGHOAMLH)`，`0x14b5dddc0` | 总量表先清空；新条目写入 config ID 与绝对总量，再刷新派生储备 |
| `MHKNMCLEABC.NKEGFKKJIFL(ONMCNLDIGJK)`，`0x14b5e0330` | 包号 24371 的有符号变化量加到现有总量，负结果截为零 |
| `MHKNMCLEABC.HLEGPHHHPJL`，`0x14b5e0050` | 从总量减去各槽位弹匣数量，得到未装填储备，最低为零 |
| `MonoTpsWeapon.UpdateAmmo`，`0x150aa2640` | 弹匣数量与储备分别写入界面的两个控件 |

因此，`TpsAmmunitionChangeNotify` 中的数量是增量；`6579` 中的是绝对总量。
服务端现有 `getReserve` 方法与 `tpsAmmunition` 存档保存的值实际对应总量，
包括已经装填的弹药。保留原方法／存档字段名，避免另起一份互不一致的经济状态。

## 修正

此前服务端先发送空的 `6579`，再通过 `24371` 只补回当前武器使用的池。
客户端会先清空全部总量，因此其他已保存、但当前没有穿戴的武器弹药池会从客户端表中缺失。

现在一次 `6579` 携带所有资源定义的弹药池，按 ID 排序并去重：

- 包括未穿戴武器使用的池，零数量也保留条目。
- 数量沿用现有资源上限和存档规则，不发出额外的“全量值作为增量”通知。
- 同步过程持有玩家锁；只读取并发送，不补满、不修改存档，也不触发保存。
- 没有当前 TPS 武器时保留原来的静默行为。
- `/tps refill` 仍明确补满资源池并保存，再发送同一份完整快照，不重建武器实体。

协议新增在 `src/main/proto/TpsRegionalPlaySupplyInfoNotify.proto`。
示例独立字节向量为 `5a0608e90770d00f5a0308ea07`：
1001 总量 2000，1002 总量 0；第二条未出现数量字段，按 protobuf 缺省值读取为零。

未穿戴武器的池 1002 应为 43，实际缺失；两次同步应有两份绝对快照，实际发送四条通知。
最初测试解码空包时的 Java 空指针已修正为读取空字节，随后保留了上述实际行为失败记录。

新增 4 项测试，覆盖原生字段向量、未穿戴／零池、重复同步／越界存档和无 TPS 武器入口。
