# 根能力记录与角色／武器覆盖参数恢复

## 已接入

每个 GameEntity 现在保存正常来源根能力的原始描述和实际实例编号。
`AbilityRootState.snapshot()` 返回不可修改的当前条目，保留编号间隙、未知能力、
自定义 override 名称及未知 protobuf 字段；已识别能力的参数读取实际运行值。
读取参数和写入参数使用同一把映射锁，避免并发遍历失效。

客户端用未知能力替换已有编号时，原实现会把旧能力留在可执行槽位。
现在该槽位改为 null，并保留新描述；旧能力已安装的效果随替换清理。
正常替换、重复确认、列表插入／移除、稳定排序、实体生命周期和施法者离场分别处理。
其他来源的 Add／Override／ReInit 消息继续由网络处理器转发，不写入普通根能力表。
头部与正文编号冲突时拒绝修改；服务端将客户端分配上限设为 65535，并一次填充稀疏间隙。
该上限是本实现的分配保护，不是 uint32 协议范围的推断。

角色的 EntityAuthorityInfo、PlayerEnterSceneInfoNotify、SceneTeamUpdateNotify 以及普通武器的
SceneWeaponInfo 已接入当前覆盖参数：

- 保留实际实例 ID，同名的不同实例分别恢复；原有天赋解锁标记按对应能力合并。
- 发送明确上报／写入的参数及相对资源默认值的变化；未改动的资源默认值不覆盖客户端初始化。
- 明确写回默认值仍作为覆盖发送，零值有效，非有限数值不进入恢复数据。
- 参数哈希必须唯一匹配；存在名称碰撞时不任意选择参数，也不发送歧义覆盖信息。
- 普通武器有 affix 不再把空能力列表标成完整初始化；TPS 原有专用初始化仍由其自身流程处理。

这些包保持 `is_inited=false`。当前实现提供根能力的覆盖信息，完整修饰器／mixin 状态表仍未生成。
记录在内存中，尚未作为跨重启存档写入 MongoDB。

## 当前原生路径

固定客户端的五个原生方法已经检查，证据为
`debug/aster-mid-20261011/batch289/root-native-verification.json`：

- `AbilityMetaAddAbility` 写入函数 `0x14b0fccb0` 使用字段 13 保存 AbilityAppliedAbility。
- `0x14f389930` 使用字段 1／2／3／4 保存名称、override、参数表及实例 ID。
- `0x14c557010` 根据快照 `0x40` 的初始化标志分流；未初始化分支可把 `0x30`
  的根能力列表交给 `0x14c550db0`，附带 true 标志。
- `0x14c550db0` 读取名称和实例 ID 构造匹配信息；上述 true 分支跳过旧根能力删除段。
- `0x14c551e10` 也按条目的实例 ID 查找能力后处理覆盖表。

这些函数仍有 ILFix 入口。本轮核对了原生路径和当前字段，没有证明实际热修复分支已执行。
