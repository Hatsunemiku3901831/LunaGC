## 保存规则

- 每个物品实例保存正整数 `saveStamp.revision` 与独立 UUID 写入标记。
  更新必须匹配原 `_id`、主人、物品类型、版本和删除状态；不能采用其他副本的新版本继续覆盖。
- 同步经济保存、普通排队保存和显式删除使用同一套条件写入。
  读取使用主节点和 majority，写入使用 majority 与 journal 确认。
- 新实例只允许插入；相同持久 ID 已存在时拒绝覆盖。旧数据在首次条件写入前保持原样，
  不进行启动时的整库重写。加载的实例固定保存目标数据库。
- 确认丢失时保留原始写入快照。重试只识别自己的写入标记；未落库的旧替换通过条件修改版本失效，
  随后的内存变更不能让旧请求再次覆盖新结果。版本溢出和无效元数据会拒绝保存。

## 删除记录与恢复

消耗到零或显式删除会在原文档写入 `deleted: true`、`count: 0`，保留实例 ID 和版本。
库存加载只选择未删除且数量大于零的记录，并增加主人／数量索引。
这些记录不占用游戏背包格，但会占用数据库空间；本轮没有自动清理删除记录，
因为过早移除会失去阻止晚到首次插入及核对已消耗奖励的证据。

通用活动领奖、新制作圣遗物及神像发出的新材料堆叠，可使用预留实例的删除记录确认：
奖励已经发出后又被消耗，恢复不会再补发一次。旧堆叠奖励依然不能仅凭当前数量推断完整交付历史。

食物退款是允许恢复原已消耗 ID 的特定路径：

1. 持久化玩家的食物退款决定，核对操作 ID、阶段、原物品 ID、主人及扣除前后数量。
2. 以原版本条件恢复原实例，并在物品写入 `foodRefundOperationId`。
3. 确认退款后清除玩家使用记录；不重新执行角色效果，不触发物品获得事件。

没有已确认的退款决定，普通保存和新预留副本仍不能恢复删除实例。
退款后的食物再次被消耗时，操作标记继续保留；原退款确认丢失也不会再退款一次。
取消尚未扣费的食物、圣遗物制作或神像供奉预留，会先确认物品版本，阻止原扣费在取消后才到达。

## 验证范围

测试使用独立随机数据库，覆盖旧副本、排队写入、删除重建、旧数据、确认丢失、晚到请求、
目标数据库隔离，以及退款、活动领奖、制作、锻造、远征和供奉等实际业务入口。
旧测试中直接调用原始 datastore 的物品种子、把删除记录装回背包的读取方式，
以及只模拟保存成功的确认故障夹具，均已调整为正式入口或真实条件写入。

最终选择的 45 个相关套件共 1,366 项测试通过，失败、错误、跳过均为 0；
其中物品保存保护 29 项，通用活动领奖 49 项。另行核对的远征／锻造 74 项、
制作／供奉恢复 83 项也通过。后两组与最终门禁有重叠，不能相加作为独立测试数。
这些结果覆盖本次选择的相关路径，未声称运行了仓库中的全部测试。
