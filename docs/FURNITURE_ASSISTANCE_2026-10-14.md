# 摆设制作协助的次数与持久化业务

## 已完成范围

新增 `FurnitureAssistance.assist(home, guestUid, now)`，保存一次协助产生的制作减时与每日次数。
这是独立业务操作，尚未绑定游戏请求；调用方仍须验证访客确实在目标家园中。
7.1 协助请求包号及响应中两个标量的业务含义未确认，本批没有猜测包号、发送通知或宣称游戏入口已可用。

| 条件 | 行为 |
| --- | --- |
| 同一访客、同一主人、同一服务端日 | 只允许成功协助一次；新开的制作任务也不能绕过次数 |
| 不同主人 | 次数独立，同一天可协助多位好友 |
| 未完成且尚未达到协助上限的制作任务 | 全部补到累计 14,400 秒减时 |
| 已完成任务 | 保持不变；没有未完成任务时返回已完成错误 |
| 全部未完成任务均达到上限 | 返回减时上限错误，不消耗访客次数 |
| 空队列、重复槽位或非法标量 | 整批拒绝，不部分修改任务 |
| 存在制作、领取、取消或批量领取预约 | 拒绝协助，保留既有经济操作的快照 |

同一好友每日一次、每天可协助多位好友依据[官方 1.5 更新说明](https://www.hoyolab.com/article/328446)。
每日边界沿用项目现有的上海时间 04:00 `GameCalendar.resetDay`；系统时钟回退不重新开放已消耗次数。
14,400 秒来自当前资源 `CONST_VALUE_HOME_ACCELERATE_PARAM = [1, 14400, 107013]`。
将它解释为每个任务累计协助上限是本批的服务端策略，结合现有原生“减时上限”错误制定，仍需请求接通后实机核对。
完成时间沿用已经核对的 `begin + duration - acceleration`，使用长整数相加。

## 保存与重试

`GameHome.furnitureAssistanceDays` 保存访客 UID 到最后成功协助日期的映射。
次数记录与所有制作槽位都属于同一个主人家园文档，在家园锁内用一次同步、要求确认的写入保存。
没有另一份访客文档需要跨文档提交，也不扣材料或发放物品。
调用方须使用服务端维护的同一份目标家园对象；本批没有增加多进程并发更新机制。

如果写入抛出异常，完整候选状态留在内存中，不单独回滚次数或再次减时。
不落库的待确认标记使后续协助先重试保存；同一访客重试只确认原操作。
冷重载只会读到旧的完整状态或新的完整状态：提交前失败可重新协助，提交后确认丢失则由已保存次数阻止重复执行。
旧家园没有次数字段时，在首个成功协助操作中建立映射。
