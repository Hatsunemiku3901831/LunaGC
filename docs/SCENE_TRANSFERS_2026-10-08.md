本批对照 [AstaPS 锁顺序与清理提交](https://github.com/MeChen618/AstaPS/commit/8e1c7b8de15e638cd3e55944cc8c4b29a1d324c0)，
接入场景互换和实体编号分配的改进，并处理相关回归新发现的 Lua 数组转换问题。

## 场景切换

此前 `Scene.addPlayer` 持有目标场景监视器，再调用旧场景的同步移除方法。
两名玩家同时互换场景会分别持有对方需要的监视器。
专项验证复现实际死锁，线程诊断显示两个工作线程彼此等待，保存在 `red-results` 的 XML 中。

现在先检查 TPS 资源，再退出旧场景，随后获取目标场景监视器进行登记和队伍初始化。
资源不可用时保留旧场景及队伍。每个玩家使用独立、非持久化的场景切换锁，
`Scene.addPlayer/removePlayer` 在同一玩家上串行执行，避免并发进入两个场景留下重复成员。
两名不同玩家仍可同时切换；重复进入和旧场景重复移除保留当前归属。
任务试用角色、TPS 武器释放、队伍恢复、活动离开回调和空场景清理保留原流程。

## 实体编号

场景创建实体时需要世界分配编号；原同步计数器会获取世界监视器。
世界进入又会持有世界监视器后等待场景，可能形成世界与场景互相等待。
额外验证直接运行 `World.addPlayer` 并在场景监视器内分配实体编号，复现第二类实际死锁。
线程诊断保存在 `world-scene-red-results`。

现在计数器使用每个世界独立的 `AtomicInteger`，分配过程不获取世界监视器。
保留类型高位和共享序号格式；八类实体同时分配的 1,600 个序号全部唯一、连续，类型高位正确。

## Lua 数组转换修正

第十五批的混合数组独立测试及当时的全量测试通过，随后本批相关回归出现截断。
核对实际依赖 LuaJ 3.0.1 的字节码，确认数组评分只检查首项，相同评分按反射方法顺序选择。
新增回归中 `{0,2.125,2.25}`、`{1,3.125,3.25}`、大整数开头的数组均丢失小数。
只增加同名表重载仍可能在大整数首项上评分相同，因此 Lua 时间轴直接接收原始参数。

`ScriptLibUserdata` 为 `InitTimeAxis` 提供原始表入口，其余字段读写和方法调用继续委托 Java 库。
上下文仍携带实际的 `ScriptLib` 接收者，兼容普通触发器、技能调用与实体控制器。
原有 Java `int[]` 和 `double[]` 两个签名保留，并单独验证可调用。
表要求连续的从 1 开始的数值索引；字符串、布尔值、空洞、零索引和额外命名字段返回失败，
已有合法时间轴保留。后续时间点的有限数、顺序和循环周期仍使用原验证。
