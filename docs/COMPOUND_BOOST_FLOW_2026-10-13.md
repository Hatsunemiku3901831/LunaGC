# 食材加工加速与自动领取

本批在已确认的加速消息与资源定义之上接入服务端流程。
请求 6991／回包 21535 注册到实际分发器，支持超燃灯、矿石消耗、分组时间调整与领取状态。

## 实现

- 持有物品 220060 才能加速；沿用正式表内全部 8 种矿石的 20／40／60 秒配置。
- 检查目标分组、解锁配方、矿石库存、队列数量、加工时间、产物配置和整数范围。
  时间副本在扣矿前生成，不能表示的时间调整不会消耗矿石。
- 局部加速按配方 ID 顺序分配同一时间预算，不自动领取。
- 全加速要求矿石预算覆盖分组最晚完成时间，限制实际用量，随后只领取目标分组产物。
- 背包满时回传 BagFull，矿石已经消耗、时间已经推进，保留完成产物供之后手动领取。
- 复用既有领取预约、实际入包确认与手册事件；按加工次数推进 `TRIGGER_DO_COMPOUND`。
  不发送重复的独立领取回包；已移除队列仍回传配方 ID 与零数量，供客户端清空对应缓存。

## 保存与失败处理

同一玩家的管理器和背包锁覆盖整个操作。持久化 `boostState`：0 可用、1 待核对。

1. 为目标分组队列预约加速，并同步确认玩家保存。
2. 检查实际扣矿数量，再同步确认矿石保存；扣完的材料栈确认删除。
3. 替换时间已调整的队列，保留预约状态并确认保存。
4. 清除预约，确认保存后再执行自动领取。

确认失败时保留待核对状态，阻止再次加速、入队和领取，避免重复扣矿或发物品。
清除预约的最终保存失败，也会恢复内存中的待核对状态。
旧 Mongo 队列没有 `boostState` 时默认为 0；待核对状态重新载入后继续生效。

这不是跨玩家／物品文档事务。部分扣矿或发奖后异常可能留下待人工核对的数据，
没有自动退款、补发或清除预约；首个预约保存未成功落盘时，重启后的状态也不能视为已确认。

## 多配方规则与验证范围

当前客户端的局部预览方法 `0x1521628b0` 逐配方消耗同一预算；
分组结束时间计算 `0x152160ce0` 取最晚时间；
发送方法 `0x152162f90` 根据所选秒数是否覆盖最晚时间设置全加速标志。
原生回包接收方法 `0x14c2558b0` 把产物列表用于获得物品提示。

本项目据此选择“局部共享预算、全加速按最晚时间扣矿并完成整个分组”的实现。
顺序及两种模式的多配方差异属于静态代码推断，尚未通过游戏内实际操作或官服服务端对照验证。
当前资源中多配方主要集中在鱼肉分组，因此这一项仍需专门验证。
领取状态数值 0／1／2／3 沿用固定 mavuika-rs 定义；原生字段标签已确认，枚举常量数值未独立解码。
本批没有重启日常服务，没有声称客户端界面已经验证。
