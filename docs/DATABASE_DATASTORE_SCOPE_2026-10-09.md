# 数据库异步操作的提交目标

## 来源与确认的问题

继续核对固定版本 [AstaPS](https://github.com/MeChen618/AstaPS/tree/932078b21b557b980c196dcc74a27cfdabaf130f)
的有界保存队列与合并逻辑。参考库和本地此前都在工作线程执行保存、删除或重试时读取全局 Datastore。
排队期间如果选择的连接或账号运行模式改变，操作可能写到另一个数据库，原数据库的进度因此未保存。
同一对象向两个数据库提交时，原合并逻辑还会丢掉其中一次写入。

这是在已吸收队列设计后发现的本地可靠性缺口。修复保留分类、容量、调用线程执行、对象锁、
失败观测和停机排空行为，没有直接替换参考库的整个实现。

## 本批变更

- `saveAccountAsync` 提交时选择账号 Datastore，保留当时的 HYBRID／DISPATCH_ONLY 路由。
- `saveGameAsync` 提交时选择游戏 Datastore；按对象类型选队列不改变数据库路由。
- 首次保存、重复键重试和并发修改重试使用同一个已捕获的 Datastore。
- 排队的零数量物品保存只删除原目标数据库中的物品，显式删除同样固定目标。
- 内置好友、邮件和任务删除固定提交目标。
- 账号清理固定游戏与账号 Datastore、MongoDatabase、UID 和账号 ID。
  排队后账号对象 ID 的修改不会改变清理对象；账号所属进度、双向好友、玩家和账号文档使用原目标。
- 合并键同时包含对象身份与 Datastore 身份；即使两个 Datastore 的 `equals` 返回相等，也各自保存。
  开始执行只移除当前目标的标记，其他目标仍可合并；正在写入的目标允许新的保存再次排队。
- 强制关闭取消所有目标的排队任务并结算 outstanding／cancelled，关闭后仍明确拒绝新任务。
- 两个 Datastore 引用使用 `volatile`，保证提交线程可见已发布的引用。

## 边界与后续

- 捕获的是数据库目标，文档内容仍在执行时按对象锁读取，未制作不可变内容快照。
- 旧数据库数据迁移、原子热重连、Datastore 关闭与连接切换协调仍需专门机制。
  仅改变引用不能保证已经关闭的旧连接完成写入。
- 账号清理仍非事务；其中一个集合失败可能留下部分清理结果，需要后续处理。
- 自定义 `asyncOperation`／`fetchAsync` 回调及同步查询自行决定连接；本批未改写任意回调的路由。
- 未初始化时提交的任务保持可观测失败，不自动等待初始化，也不转写后来选择的数据库。
- 不提供离线持久化日志、自动重放、所有线程间的写入排序或完整数据库故障恢复保证。
- 日常游戏与 Mongo 的身份、启动时间和健康状态保持原样；本批没有迁移日常数据、部署、提交或推送。
- 调查修饰器定时期间发现客户端动作所有权与隐藏队伍角色的效果寿命仍需明确，
  本批未接入 duration／thinkInterval／onRemoved，不能据此认定完整技能生命周期已经完成。

其他参考库、技能、历史活动、商城 SDK 和千星奇域的完整接入目标仍在进行。
