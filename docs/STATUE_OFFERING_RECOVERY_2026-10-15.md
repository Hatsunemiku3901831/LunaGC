# 中断供奉的核对与恢复

供奉中断后继续保留城市中的 `pendingOffer`，普通供奉和管理调级不会覆盖这条记录。
本次为新供奉增加经济快照，并接入按操作 ID 执行的管理恢复。
默认奖励仍来自资源原值；可选增强策略没有改变。

## 命令

沿用 `statue`／`sots` 的目标选择和 `player.teleport`／`player.teleport.others` 权限：

| 命令 | 效果 |
| --- | --- |
| `statue @10001 city 1` | 查看城市状态及待处理操作 ID |
| `statue @10001 audit 1` | 只读核对记录、成本、奖励快照和数据库一致性 |
| `statue @10001 resume 1 <operationId>` | 补齐同一次供奉尚未完成的扣除、奖励与进度 |
| `statue @10001 cancel 1 <operationId>` | 取消成本、奖励、体力均未改变的预留 |

目标必须在线。恢复／取消要求玩家位于自己的世界及记录中的场景。
操作 ID 必须完全一致；完成后再提交同一 ID 会被拒绝。
已扣费的记录不能通过取消来退款，使用恢复完成原供奉。

## 保存与核对

新记录使用 `version=1`，预留前冻结以下内容：

- 成本物品的 Mongo ObjectId、扣除前数量与消耗量；运行时 GUID 在重登后改变不影响核对。
- 每项奖励的前后数量；材料已有堆叠沿用其 ObjectId，新堆叠提前预留 ObjectId。
- 阅历奖励的前后冒险等级与该等级内阅历，正确识别跨级后的阅历减少。
- 城市进度、体力上限、场景、区域及解除区域限制的动作。

正常供奉和恢复共用冻结奖励的逐项发放逻辑。材料写入／删除与玩家属性写入分别得到同步确认。
恢复先等待已有异步写入排空，再核对内存和数据库中的相同记录、唯一堆叠、持久 ID、数量和属性。
全部核对及剩余奖励的资源／容量预检通过后，才开始新的扣除或发奖。
成本和奖励只能处于各自冻结的前值或后值；已完成的项不会再次执行。
已应用城市进度的记录必须同时具有完整成本、奖励与体力结果，然后仅清除记录。
恢复完成后同步城市状态，并沿用正常升级的区域、任务、见闻和事件入口。

只读审计使用玩家文档字段投影，不解码另一份完整 Player，也不创建缺省城市或保存玩家。
管理恢复与普通供奉共用库存锁。保存未确认时继续保留记录；内存与存档不一致时要求先重登。
这不是跨集合事务，也不保证外部插件或任务事件恰好执行一次。

## 保留待人工核对的情况

- 旧记录没有成本／奖励的持久 ID 和完整前后快照，保留 `version=0`，拒绝自动补发或取消。
- 成本被替换为另一堆叠、出现多个同类堆叠、奖励余额被其他玩法改变、体力上限改变或玩家记录不一致。
- 待补发物品的资源类型发生变化、阅历升级曲线改变，或剩余奖励超过容量／数量上限。

目前资源中的 1–8 号城市使用普通材料、阅历及原石奖励，均适用新记录。
自定义资源若加入圣遗物等奖励或让奖励与供奉成本重叠，仍使用原有故障保护，不虚构可恢复的身份。
余额快照不是完整收支账本；核对失败时应保留记录检查原因，不能通过改余额凑齐数值来代替核对。
排期或倍率配置后来改变，不会重写已冻结的奖励。
