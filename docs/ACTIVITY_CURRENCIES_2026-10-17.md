# 活动货币与排期余额

## 来源

当前资源声明了 45 种 `activityCoinIdList` 货币。另有 22 种旧活动货币仍出现在原始商店费用中，
可以通过商店原始排期和历史活动目录确定所属活动。
例如 128 属于 2006「谒索雷痕」，141 属于 2014「远海诗夏游纪」。
此前这类虚拟物品会被背包入口接受，但没有执行任何余额变更。

本轮接入这 67 种货币的活动存档、背包收支和现有活动信息通知。
没有为它们编造玩家属性编号，也没有猜测缺失的 `ActivityCoinInfoNotify` 字段。
当前协议的 `ActivityInfo.activity_coin_map` 字段号为 1715，本轮复用该字段和 `ActivityInfoNotify`。
未归的熄星 109／110 沿用已有的阶段奖励与消费账本，不建立第二份余额。

完整编号、所属活动、原始费用行及文件哈希见[资源审阅表](data/activity-currency-bindings-2026-10-17.json)。
可重新核对：

```powershell
python tools/audit_activity_currencies.py --resources resources --output docs/data/activity-currency-bindings-2026-10-17.json --check
```

## 已接入的行为

- `ActivityData` 读取现代货币声明；旧货币从已加载的原始商店费用中识别，不从 GM 修改后的价格推断归属。
- 排期配置同时发布不可变的货币归属表。归属冲突、将全局货币声明为活动货币等错误会拒绝替换配置。
- `PlayerActivityData.activityCoins` 保存余额。旧档缺少字段时按 0 读取，空任务列表在冷读、关闭及恢复时也可正常使用。
- 只有活动开放、玩家归属正确且存档排期一致时才能增减余额。过期、关闭或旧排期不会接受发奖或消费。
- 正常关闭后重新开启沿用原余额；重新复刻创建新排期并清零，沿用原活动文档 ID。
- 背包给予与计数入口识别活动货币，不生成物理堆叠。未实现的虚拟物品返回拒绝，避免成功提示掩盖空操作。
- 单项消费及数组／迭代器批量消费均接入；相同编号先合计，再检查数量、余额和整数边界。
- 同一活动的多种货币在同一文档内确认扣除，随后处理普通费用。当前资源没有跨活动联合费用，涉及多个活动文档的批量扣除会整体拒绝。
- 整批奖励容量检查会拒绝无法接收、活动关闭或溢出的货币，避免收费后跳过它们。
- 活动存档的余额写入和后续保存使用多数确认与日志写入，避免旧的排队存档覆盖余额。
- 余额写入与排期刷新共用库存锁；涉及活动管理器时按库存、管理器、活动文档的顺序加锁。
- 成功后发送现有活动信息；通知异常记录日志，已确认的余额变更仍返回成功。

## 尚未完成的范围

确认写入异常时，服务端保留尝试后的余额，不自动恢复旧值；同一活动文档在当前会话中停止后续收支和保存，
防止在确认结果未知时继续叠加操作。两种“写入前失败／写入后确认丢失”均有注入测试，普通费用不会继续扣除。
这仍不等于跨重启或多进程的结算恢复。持久化操作 ID、明确核对／恢复入口，以及完整商店付款、发货、退款和任务领奖事务仍需继续接入。

后续已补齐[活动整份存档版本保护](ACTIVITY_SAVE_FENCE_2026-10-17.md)，防止冷读旧副本及排队写入覆盖
较新的余额或复刻排期，并核对保存应答丢失后的同文档写入身份；完整业务事务仍按上述范围继续接入。
活动货币的[持久化计划及按操作 ID 恢复](ACTIVITY_COIN_RECOVERY_2026-10-17.md)也已接入，
准备／余额写入不明时，重连仍保留冻结；恢复入口只处理活动余额，完整付款与发货仍需继续核对。

本轮没有还原这 67 种货币所属活动的全部任务、玩法、兑换条件和奖励上限。
旧活动没有进入通用声明的其他货币、熄星账本与普通给予入口的统一，以及当前客户端的实际展示和收支表现仍需继续验证。
