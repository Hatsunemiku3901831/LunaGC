# 最近有效锚点复活

## 来源与问题

参考 AstaPS 固定提交 `7cc148d1f752a43d4b9146b3b73f26875902546f` 的
`RespawnPositionHelper` 和 `TeamManager.respawnTeam`，接入最近已解锁锚点的选择。
本地旧代码只接受 `SceneTransPoint`；当前场景 3／5／6 的资源分别有
709／28／15 个 `TransPointNormal`，无法通过旧筛选。
查找抛错后又使用场景 3 的开场坐标，其他场景也会收到错误的进入场景通知。

同时修正本地复活路径中的两处问题：

- 查询返回共享资源坐标，且通知和玩家位置各查询一次，可能出现坐标不一致。
- TeamManager 与大世界请求处理器各发送一次 `WorldPlayerReviveRsp`；副本复活还会收到这个不相关的响应。

## 行为

- 从当前场景的永久解锁记录中选择锚点；任务强制锁定的锚点不能成为候选，解锁进度保持原值。
- 接受当前 `TransPointNormal` 以及旧版 `SceneTransPoint`／`TransPoint`。
  不把名称包含 `TransPoint` 的任意类型都视为锚点。
- 跳过缺失点位、缺少 PointData、编号不一致、其他场景的记录及跨场景目的地。
- 优先使用有效的 `tranPos`，缺失或包含非有限数时尝试 `pos`；两者均不可用时跳过。
- 按传送目的地的三维距离选择最近点；距离相同则按点位 ID 决定，避免受存档插入顺序影响。
- 返回独立位置快照。复活只选取一次，进入场景通知和玩家位置共用这个快照。
- 无可用锚点时在当前场景原位置复活。通知抛错会交回调用方处理，不再触发开场海滩回退。
- 保留已有的 40% 生命恢复、死亡标记清理和饱食度处理。
  大世界与副本请求处理器分别发送自己的响应。
