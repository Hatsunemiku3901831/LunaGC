# 指定连接的 RPC 与异步回复上下文

## 核对与复现

继续核对 AstaPS 固定提交 `7cc148d1f752a43d4b9146b3b73f26875902546f`
和本地分离服务链路。参考实现使用包号回调和广播，本地此前已增加逐次请求标识。
但服务端尚无指定连接的请求接口，回复上下文也仅保存在接包线程。

两个失败对照均复现了工作线程回复缺少 `responseTo`：单请求，以及两个连接反序完成。
本批增加显式捕获接口，并将这两个调用用例改为在处理器内捕获、在工作线程回复。
普通异步发送不会自动继承接包线程的上下文。

## 接口与连接归属

- `DispatchServer.asyncTo` 只向指定的、属于该服务端且已经认证并打开的连接发送请求。
  请求 UUID、预期响应包号、连接对象和连接代次共同参与匹配；其他连接的同 UUID 回复不能完成请求。
  发送前再次检查代次与认证，失败时不会退回广播。
- 连接关闭或重新打开时，旧代次的定向等待失败并清理登记，不影响其他连接和旧式通知回调。
  取消、超时、发送异常和解析异常继续清理各自的等待。
- 在关联请求处理器中调用 `captureReply()`，得到可以交给其他线程的 `DispatchReply`。
  它固定原服务端／客户端、连接、代次、请求 UUID 和声明的响应包号，不再依赖回复线程的上下文。
- `DispatchReply.send` 只有一次发送尝试。已关闭、代次被替换或失去认证的连接不能发送；
  发送抛出异常后也不会再次发送可能重复的回复。捕获时已经更换连接则拒绝原请求。
- 两端均在连接打开／关闭时管理代次。客户端重新打开时清理旧等待，关闭时清理代次与等待。
  不再为没有当前所属游戏服的旧客户端启动重连任务；延迟任务也会再次检查所属对象。
  完整重连接管仍需继续完成。

示例：在接包处理器里捕获上下文，再交给业务自己的执行器：

```java
var reply = dispatcher.captureReply();
executor.execute(() -> reply.send(result));
```

该对象只负责回复的协议归属，不传递数据库屏障或游戏线程上下文，
也不会自动取消已经开始的业务。业务仍需执行自身的准入和权限检查。

## 验证

- 新增 30 项检查：指定连接、错误来源、关闭／重开、失去认证、外国连接、
  登记与发送之间断线、取消／超时／异常、48 个并发反序回复、一次回复尝试及有符号包号。
- 使用实际 `DispatchServer`／`DispatchClient`、JSON／XOR 编解码和处理器，
  字节连接由可控替身提供。实际客户端工作线程的回复能够完成服务端指定连接的等待，
  其他连接不能代答；客户端关闭与重新打开后不能使用旧回复句柄。
- 最终通信专项六套、129 项通过；相关回归 26 套、521 项通过，失败、错误与跳过均为零。
- 初次扩展夹具替换底层连接时没有恢复认证标记，三项失败；
  另一项错误调用了没有插件管理器的真实通知事件。这四项夹具问题已修正，原结果保留。
  门禁准备曾误算新增用例数，未执行测试；最终数量按 XML 的 30 项核对。
- 2,708 份 Java 主代码与测试文件匹配构建副本（允许换行差异），应用类匹配编译输出。
  相对上一构建，类改动仅属于本批六个生产源码，新增加三个类，默认资源不变。
  资源子模块、外部开发资源和九个参考库均保持原固定提交且工作区干净。

## 后续业务接入

本批提供可用的定向请求和跨线程回复接口。现有广播调用方尚未全面改为指定服务器，
内置／自定义异步处理器仍需逐项迁移。密码重置的跨服主动撤销、逐服确认、
账号来源与连接代次绑定、完整重连归属，以及真实多进程故障时序仍未完成。

本地测试没有启动独立 WebSocket 集群或游戏客户端，不能证明此前报告的游戏错误已解决。
