# 通用活动任务领奖的保存与恢复

## 本轮改动

此前默认领奖路径逐项构造奖励、调用背包批量添加后保存领取标志。
背包拒绝部分物品、数量被截断或保存失败时，可能少发奖励，或在重试时重复发放。
本轮在 `PlayerActivityData.takeWatcherReward` 的默认活动路径接入：

- 校验玩家、当前活动实例、复刻排期、任务归属、停用标记与完成进度。
- 发放前检查整批奖励的原始数量、重复物品合计、背包容量与堆叠上限。
  不支持的物品或虚拟奖励会拒绝整批领取，保留任务领取状态。
- 先确认保存冻结的奖励计划，再逐项记录开始发放和完成确认。
  武器等装备按数量生成独立实例，并保留计划中的持久 ID 与初始属性。
- 每项物品及相关玩家数据确认保存后才推进领取进度。
  最后将完整结果与任务已领取标志写入同一活动文档。
- 未确认计划保留到重连，阻止普通活动保存与重新复刻覆盖；防止库存通知回调重入领取。
- 活动货币使用领取计划中预留的操作 ID，沿用已有的活动货币恢复机制。
  与领取关联的货币计划不能单独取消。

未归的熄星 `2001` 继续使用独立领奖路径。本轮没有改动奖励数值、协议定义、资源仓库或客户端补丁。
设计继续参考固定版本 AstaPS 的 `RewardGrantJournal` 所强调的保存意图与确认顺序；
本项目使用现有活动文档版本校验实现，不能据此宣称全部经济事务已完成。

## 恢复命令

在 GM 顶部选择在线玩家 UID，使用：

```text
activityrewards pending
activityrewards audit <activityId> <operationId>
activityrewards resume <activityId> <operationId>
activityrewards cancel <activityId> <operationId>
```

权限为 `server.activityrewards`，操作其他玩家为 `server.activityrewards.others`。
`pending` 包括已经关闭的活动；`audit` 只读。
`resume` 继续原计划中可确认的阶段，不能通过更改操作 ID 另发一份奖励。
`cancel` 仅允许尚未开始发奖的计划；已发放奖励不能用此命令撤销。

新装备、新堆叠物品可以凭预留实例 ID 核对，唯一外观可以通过幂等解锁继续，
活动货币可以按关联操作 ID 恢复。
旧堆叠和普通全局货币在“已开始、结果不明”状态下，不以当前数量猜测是否发放；
会保留计划并要求核对。该状态尚未实现跨物品与玩家文档的自动完整恢复。

## 验证与边界

先保留旧业务路径的失败测试，再通过真实背包与隔离 Mongo 数据库检查保存失败、
确认丢失、晚到写入、冷读、装备实例、外观、活动货币、排期与任务归属。
最终相关回归为 19 个套件、362 项测试，失败、错误、跳过均为 0；其中本轮通用领奖 48 项。
旧业务路径首次复现为 11 项测试中 10 项断言失败，原始测试源与结果均保留。
后续扩展中验证了预留实例能够安全完成冷读核对，以及货币清理失败可以随下一次保存确认，
这两类正常恢复不会再被要求一律返回失败。

证据保存在本地忽略目录 `debug/aster-mid-20261011/batch342/`。
测试未使用实际玩家数据库。旧 `ObjectId` 类型活动 ID 的额外夹具在解码阶段失败，
没有到达业务路径；该尝试没有计作业务复现或本轮兼容性通过项。
