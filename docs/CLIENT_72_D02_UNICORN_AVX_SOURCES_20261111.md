## 译码与 hook：观察和有条件推断

既有本机观察由主线提供：固定 Unicorn 2.1.4、默认模型 19/Haswell、`CR4=0x50200`，原指令在 code hook 报宽度 4、invalid hook 触发并返回 `UC_ERR_INSN_INVALID`；外部解码器将其识别为 6 字节 `VINSERTF128`。本次没有重跑该观察。

以 2.1.4 源码中的正常 64 位 VEX 路径为条件，`C4 E3 7D 18 …` 可以这样解释：

1. [translate.c 4933–4989](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L4933-L4989) 读取 3 字节 VEX 前缀；第二字节的 map 值 3 进入 `0x13a`，第三字节 `0x7d` 的 L 位为 1、pp 值为 1。[分派](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L9139-L9155) 到 `gen_sse`。
2. [translate.c 3324–3360](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L3324-L3360) 先做 SSE 表及 TS/EM/OSFXSR 检查；当这些前置条件允许继续，[3382–3390](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L3382-L3390) 把第 4 字节 `0x18` 暂存到该层的 `modrm` 局部变量，随后因 `vex_l != 0` 直接生成非法指令。这里的 `0x18` 是 map 0F 3A 的 opcode；原指令真正的 ModR/M 和立即数尚未被此路径读取。读取的是代码字节，不是操作数数据内存。
3. [translate.c 4818–4830](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L4818-L4830) 先生成占位 code hook，[9170–9184](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L9170-L9184) 在 `gen_sse` 返回后将大小设为当前译码 PC 减起始 PC；按以上路径为 4。非法分支生成 [#UD](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L1464-L1479)。这能解释既有宽度 4、无操作数读写和非法现象，但本次未取异常到 Unicorn 错误码的完整调用链，也不能仅凭症状证明本机 DLL 必经同一构建。
4. 对这条 opcode，仅去掉 L 位拦截也不足以实现它：继续下去的 [0F 3A 分支](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L4404-L4419) 会读取真实 ModR/M 并查询表，而 [table7](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L3284-L3309) 没有 `0x18` 项，空项走 unknown/illegal。这里说明的是这个译码分支及 opcode，不概括所有 VEX 指令。

## CPU feature、XCR0 与公开控制

- [Haswell 模型表](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L2236-L2254) 声明 XSAVE 和 AVX；这不是最终 CPUID。[TCG mask](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L602-L613) 包含 XSAVE 但不包含 AVX。源初始化先展开再过滤：[cpu.c 4824–4826](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L4824-L4826)、[4784–4795](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L4784-L4795)、[3816–3824](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L3816-L3824)。在 `force_features` 为 false 的条件下，最终 leaf 1 AVX 位被清除，而 XSAVE 可保留；leaf 1 的 OSXSAVE 由 XSAVE 和 CR4.OSXSAVE 动态决定，见 [4032–4039](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L4032-L4039)。位定义见 [cpu.h 598–600](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.h#L598-L600)。
- [默认选择](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L5072-L5095) 已是 Haswell。YMM 状态位是 XCR0 bit 2，[定义](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.h#L481-L493) 与 [YMM 对 AVX feature 的关联](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L1202-L1220) 可查。正常 reset 后 XCR0 依过滤后的 feature 设置，[4540–4562](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L4540-L4562) 中 FP/SSE 两位由相应 feature 得到，YMM 位依 AVX 得到。若采用上述普通过滤且无其他状态覆盖，默认 Haswell 源码推演 XCR0 为 `0x3`，而非 `0x7`。这是源码条件推断，不是本次实机读数。
- 注意顺序：[扩展组件先按模型特性生成](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L4630-L4650)，[随后过滤](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L4824-L4826)，但组件低字自身的 TCG mask 为 [全 1](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/cpu.c#L953-L960)。因此默认 Haswell 的 CPUID `(0xD,0)` 组件位可能保留 YMM，和最终 leaf 1 AVX、reset XCR0 的取值不是同一判断；应由独立 CPUID/XGETBV 实测对照。源码中 `XGETBV` 和 `XSETBV` 的译码入口还分别检查 XSAVE/前缀及后者 CPL，见 [translate.c 8128–8155](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/qemu/target/i386/translate.c#L8128-L8155)；本次未取得 helper 文件，不推断其全部运行时校验。
- 在已取的 `cpu.c`、`cpu.h`、`translate.c` 中检索不到 `HF_AVX_EN_MASK`；这条失败路径的明确拒绝条件是上面的 `vex_l` 分支，不能套用另一份 QEMU 版本的 gate。本机随附头经 CRLF 归一后，其 `x86.h` 和 `unicorn.h` git blob 分别匹配 tag tree 的 `51917431338133097a035d4f5514f5e215b5fe07` 和 `b4ffc6bc75ff865f04fa8cfc12b6743404599ecf`。头文件列有 [CR4、YMM 寄存器 ID](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/include/unicorn/x86.h#L138-L143)，[YMM0 起始](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/include/unicorn/x86.h#L224-L231)，未见 XCR0 寄存器 ID；存在 YMM 接口不证明指令可执行。模型控制需在初始化前设置，见 [unicorn.h 578–583](https://github.com/unicorn-engine/unicorn/blob/8028ec436f2d9376525352dd38ed9ed6b9f6be10/include/unicorn/unicorn.h#L578-L583)。本次未审核 `unicorn.c` 或库中的具体寄存器分派实现，不声称已穷尽所有控制手段。

## 下一步合同与未知项
