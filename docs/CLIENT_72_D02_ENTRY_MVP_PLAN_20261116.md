# D-02：先实际入场的最小实现路线

## 用户授权、目标与当前状态

2026-11-16用户最新指令：缺失部分优先自行开发，数值可由智能体决定，先进入游戏，其余后补。技术复核基线`7b2ed77`；本次只做状态分析与规划，没有修改运行代码、资源、Proto或数据库，没有部署/客户端验收。

新增中间出口`D02-M0`：在独立portable实例和新测试号上，经正常认证、显式选人/命名、必要初始化与场景握手，看到角色实际落地；随后验证10分钟心跳及该新号正常退出重登。首次可见落地即报告实际进展。完整D-02仍保留原六项和旧号保存恢复，M0不能代替它。任务状态、完成标记只以Project为台账。

这改变了过去“完整旧号全部资源、每个原版字段及完整客户端内部构造研究都必须先闭合”的首发排期。旧研究证据和未解问题保留，但未被所选新号入场实际需要的项后移；服务器业务模块可以自行实现，参数可以采用明确的临时服务端策略，不必先还原对应原版资源字节。

## 首个可实现配置

- 使用新的隔离测试账号和数据库，不改已有mongodata/local/data，不清空或裁剪所选旧号。第一次用普通出生角色，无圣遗物、无特殊能量角色、无额外收藏角色，只保留实际出生装备。
- 优先沿正常选人流程选女主`10000007`，初始Scene3和位置复用当前Player/GameConstants实现；初始武器优先复用既验11101。它们是当前服务端候选和已有资源，不是本次新的客户端验收。实施时一次核对角色→depot→技能→武器→模型/ability→场景引用，不臆造客户端没有的ID或资产名；具体depot沿真实选人/questing分支确定。
- 最小入场模式必须显式启用，资源/配置/存档仅落独立InstanceRoot。优先复用现有入口和真实ResourceLoader；若现有全量加载/登录耦合阻挡，按明确的所选功能依赖实现独立的M0加载/就绪判定，不手设loadedAll或将全量ready改为成功。
- 资源可以来自既验片段、适用的具名候选JSON或自主编写的服务端表。至少区分`target-verified`、`upstream-candidate`和`server-provisional`三种来源，记录真实字段、引用和临时策略；候选/自定值不回写成原版恢复成果。无需为此建立通用多版本框架。

## 最小部署与实机的真实前置

M0部署不要求旧号全121角色恢复、全部四族二进制解析或全量R4通过，但必须满足所选新号路径本身的登录认证/会话、必要包号及wire、资源引用、场景实体构造和错误处理。未知但必需的协议字段继续是阻塞；已证可后移的业务功能可以在显式模式中关闭，也可编写正常的空列表/未开放响应，不能伪造未知协议成功或无条件吞异常。

正常服务器实现无须逐个复刻客户端内部allocator/parser；可利用已有真实协议证据实现独立服务端，再通过目标客户端消费验证。但本计划不解除原A/B、preview及准确被拒动作和依赖，也不自动授权Daybreak或以模式更名重试。不能绕过原生认证/信任/校验。

ResourceLoader.loadAll当前在完成其初始化序列后设置loadedAll；HandlerPlayerLoginReq会检查它。不得只改布尔值使登录通过。如采用有限加载，必须明确为M0范围、实际检查该范围的依赖、隔离于正式全量状态，并用缺必需资源会拒绝的实际测试证明其语义。完整D-02的ready仍独立保留。

需要用户操作前备齐实验，说明操作、预期、反馈和正常退出，取新实时ready。禁止computer-use；窗口化2560×1440仍需核实。M0代码/资源尚未实现，当前没有现成可直接启动的实例。
