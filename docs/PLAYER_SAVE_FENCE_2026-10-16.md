# 玩家整份存档的版本隔离（2026-10-16）

## 已复现的问题

之前 `saveGameSync(Player)` 和普通后台保存都直接替换整份 `players` 文档。
同 UID 的两个 Player 副本没有共同版本检查。真实 Mongo 的六项初始测试中，四项失败：

- 已经落库的新弹药和经济进度，可被旧副本的同步保存覆盖。
- 队列中等待的旧副本，可在新的确认写入之后覆盖整份文档。
- 已经读出的 Player 在数据库记录删除后，可以通过普通保存重新插入。
- 新建的同 UID 对象可以直接替换已有玩家。

读取旧存档不写回、同一活动对象的排队保存保留最新状态，这两项初始检查通过。
原始 RED 在 `debug/aster-mid-20261011/batch305/red-results/`，没有将这两项计为缺陷。

## 保存规则

`DatabaseHelper` 的同步、普通后台和 `Player.save()` 入口现在使用同一个 `PlayerSaveGuard`。
每份完整结果都有 `saveStamp`：递增的 64 位版本及新生成的 UUID 写入标识。

- 已读取的对象，只能在 UID 和原版本／标识仍相符时替换文档；不使用 upsert。
- 新对象只做 insert；重复 UID 会失败，不再按重复键重试整份覆盖。
- 删除后的旧对象不能重建记录；新程序创建的同 UID 玩家具有不同 UUID。
- 冲突后保留失败状态，不自动读取新版本来覆盖数据库；上层需要重新读取并判断操作。
- 普通保存仍使用原来的有限队列、合并规则和入队时捕获的 Datastore。
  同一对象正常确认后可以继续保存；已经绑定的对象拒绝改投其他 Datastore。
- 编码前后的版本管理分开。后台编码遇到集合并发修改，保留原先有限重试；
  没有发出的写入不会消耗版本。新玩家 UID 分配在返回登录流程前确认初次保存。

旧文档缺少 `saveStamp` 或显式存为 null 时，读取仍不写入。
首次显式保存以“UID 匹配、标识仍缺失”为条件，原子替换完整文档并写入第一版标识。
两个旧副本也只能有一个成功。没有全库迁移或读取时自动保存。

核对了当前依赖 Morphia 2.2.7 的实际字节码：其 `@Version` 首版走 insert，
异常回退也不覆盖所有运行时异常。因此这里使用 Morphia 编码、Mongo 条件写入，
没有直接给旧 Player 添加 `@Version`。其他实体的保存方式保留原实现。

## 写入确认不明与晚到请求

每个活动对象只保留一个冻结的候选 BSON、原版本与候选写入标识。
写入异常向原调用者传播；后续保存必须先用主节点的原始元数据读取核对：

1. 数据库标识恰好是自己的候选：接纳自己的已提交版本，再保存当前状态。
2. 数据库仍是原版本：以相同原版本条件只更新 `saveStamp`，淘汰可能晚到的旧替换。
   这一步保持业务字段不变；旧替换和这一步只能有一个先成功。
3. 旧替换先成功时，重新核对自己的候选标识；标识更新先成功时，旧替换再到达也无法匹配。
4. 这次元数据更新本身确认丢失时，继续保留它的 UUID，下一次只认自己的标识。
5. 新玩家初次 insert 不明时，只重试原冻结文档；唯一 UID 防止它替换已有记录。
6. 读取失败、记录消失或发现其他副本的标识时，拒绝继续覆盖。

完整保存及元数据更新使用 majority+journal；核对使用 primary+majority。
正常路径只有一次完整文档写入，没有增加正常保存前的数据库读取。
临时冻结结果和 guard 不进入玩家 BSON，已完成结果也不累积历史列表。
