# 账号保存版本与登录令牌确认

## 来源和复现

继续核对 AstaPS 固定提交 `7cc148d1f752a43d4b9146b3b73f26875902546f`
的账号创建、删除与 `AccountPasswordResetService`。参考的密码重置会排空写入、
同步修改凭据和令牌；本地普通账号保存仍会整份覆盖、允许重新插入，并且异步返回。
直接移植重置操作后，旧副本仍可能把旧凭据写回，因此先补齐账号保存本身。

对上一版已验证构建执行 15 项检查，12 项断言失败、3 项对照通过，错误和跳过均为零。
复现范围包括旧副本覆盖新密码／令牌／权限／封禁、已排队旧副本、删除后再次保存、
未建档对象保存、跨库保存、旧档竞争和三种令牌尚未写入就返回。

另有 5 项国服 SDK 检查，其中 3 项断言失败、2 项对照通过：
密码和手机登录在独立账号库配置下仍额外把账号写入游戏库；恢复令牌先返回再异步保存。

## 保存入口

- `Account` 从 Mongo 读取时保存原 Datastore、账号 ID 与当时的版本。
- 新账号由原有创建服务保留编号和唯一索引检查，以单次插入写入初始版本；
  只有插入得到确认后，才把账号作为可保存对象返回。
- 普通账号保存只按原版本条件替换，不执行 upsert 或插入。
  过时、已删除、修改 ID、跨 Datastore 或从未确认创建的对象都会拒绝。
- 账号队列、同步账号保存、通用游戏保存的 Account 分支都使用相同保护，
  不会把版本冲突重试为无条件替换。
- 同一个活跃对象向同一数据库重复排队仍会合并；原有分队列和提交时固定目标保持有效。

每次写入使用递增 int64 `saveStamp.revision` 和唯一 `saveStamp.token`。
仅有相同版本号不足以视为同一次写入；新建记录拥有独立令牌。
缺少版本的旧档可读取，查询不会触发迁移；第一次成功更新按缺少版本的条件晋升，
两份旧副本只能有一个成功。

## 不明写入结果

写入异常会保留原始条件、确切文档与本次写入令牌。重试前先读取已存版本：

1. 识别出本次写入已经提交时，接受自己的结果。
2. 仍是原版本时，先用一次只修改元数据的条件更新，使旧的延迟替换失效。
3. 遇到另一副本的版本、已删除记录或读取失败，拒绝继续覆盖。

元数据更新自身的确认也可能丢失，使用同一令牌重新核对；
不会采纳其他账号副本的最新版本来绕过冲突，也不会按当前字段值猜测写入结果。
这不是跨文档事务或多进程生命周期锁。

## 登录路径

普通 session key、`v2_` session key 和 combo login token 都在确认保存后才返回，
即使账号异步队列繁忙也不依赖排队完成。
国服密码／手机登录移除了额外的原始游戏库保存；令牌恢复中的字段更新使用同步账号入口。
分库测试保留了游戏库同编号的另一份记录，实际凭据只写入选定账号库。

本轮保留原有密码认证、短信和宽松令牌接纳策略；没有将它描述为密码重置或全面撤销旧登录资格。
密码重置的同步业务操作与认证策略仍需继续适配。

## 继续核对的边界

任意插件或原始 Mongo／Datastore 写入仍可绕过该保护。
普通异步 `Account.save()` 的冲突会计入队列失败；需要立即确认结果的调用方应使用
`saveAccountSync`，冲突后重新读取并重新决定操作，不能直接把旧字段合并回去。
只由 JSON 构造而没有数据库加载状态的 Account 不作为可写对象，分离服务的远端副本更新仍需适配。

完整登录后半段、缓存账号在其他副本更新后的处理、密码重置、重连接管、
多服务真实故障切换和客户端登录仍需继续核对。
本轮没有启动游戏，也没有宣称此前反馈的游戏错误已经修复。
