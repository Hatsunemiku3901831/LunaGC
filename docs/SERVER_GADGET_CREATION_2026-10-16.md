# 道具生成方与无相复苏多实例

核对 AstaPS 固定提交 `7cc148d1f752a43d4b9146b3b73f26875902546f` 的
`EffigyCombatHelper` 和 `ActionCreateGadget`，参考对复苏棱晶的重复编号处理指出了一个本地缺口：
本地创建动作已经解析 `byServer`，但生成与旧对象替换逻辑没有使用它。

当前资源中的 `Monster_Effigy_Electric_CreateRebornPart1/2/3` 分别包含 1、2、3 个
`CreateGadget` 动作，均使用 `42004010`，且明确 `byServer: true`。
同一主人、同一道具编号只留一个的旧处理，会在创建第二、第三个时移除前一个。
精英版还使用 `42004016/17/18`，同样需要按配置保留实例。

## 实现

- `byServer: true` 优先于客户端对象编号及客户端召唤链判断。
  明确要求服务端生成的动作正常创建每次请求的实例，不互相替换。
- `EntityGadget` 记录服务端能力配置给出的生成标记。
  标记不来自客户端创建通知，也不增加网络协议字段。
- 客户端副本清理和旧替换路径保留这些明确的服务端对象。
- 按当前七份无相能力资源区分客户端对象：无相之雷的发射器／防御部件，
  以及雷、风、水、冰、火、草使用的 `42004012` 位置标记由客户端创建。
- 初始位置标记 `42004006`、复苏棱晶等明确标为服务端创建的动作继续生成。
  其他怪物或无关道具继续使用现有创建路径。

当前资源的生成声明决定处理方式，因此同一个编号仍可以在明确的服务端动作中生成。
生成位置沿用既有原生位置负载与出生规则；棱晶测试提供了各动作的独立位置负载，
未将角色骨骼挂点的位置推断当作已完成。
