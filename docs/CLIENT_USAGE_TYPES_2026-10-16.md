# 从 TypeInfo 单元核对原生消息工厂

新增只读工具 `tools/extract_client_usage_types.py`，沿当前 7.1 客户端的元数据使用记录，
将原生代码读取的具体 TypeInfo 单元反查为类型定义，并在存在明确字面量 getter 时读取包号。
这样可以区分构造布局相似、实际消息类型不同的入口。

## 使用

```powershell
python tools/extract_client_usage_types.py --binary "<客户端目录>/YuanShen.exe" --metadata "<客户端目录>/YuanShen_Data/Native/Data/Metadata/global-metadata.dat" --cell 0x1457b3fd8 --cell 0x1457b4058 --output debug/factory-types.json
```

输出目录应已存在。省略 `--output` 时向标准输出写 JSON。
当前配置只接受 `extract_client_type_names.py` 记录的两份输入 SHA-256；
这不是适用于所有 7.1 构建或其他版本的通用解码器。
不支持的方法、字段、字符串缓存及泛型类型单元会明确报错，不按相同数字或相似结构冒充消息类。

## 当前核对

| 工厂读取的单元 | 类型定义 | 原生名称 | 字面量包号 |
| --- | --- | --- | --- |
| `0x1457b3fd8` | 42260 | `INNLOCEGCPC` | 5729 |
| `0x1457b4058` | 36283 | `JMKPIKBLLBH` | 27235 |

第二项与现有常驻千音雅集开始消息吻合。第一项是另一种请求，仍需核对消息字段、响应与玩法归属。
单凭调用参数同为编号／布尔值，无法将它们视为同一协议。

原生依据包括：

- `0x1402f3730` 注册使用缓存描述符，具体类型缓存由 `0x142871c08 + 0x50` 指定。
- `0x140524250` 解码每个使用项的缓存种类、目标索引和来源索引。
- 目标编号 11275 同时出现在字符串、方法与类型缓存中；只有种类 1 能用于本工具的具体类型解析。
- 来源索引继续经过已注册类型引用表核对，最后读取命名类型定义。
- 包号来自该类型的 `AEGNNPENLNM` 无参方法，并只接受 `mov ax, imm16; ret` 的五字节形状。

当前搜索从已配对的使用项表起点到元数据文件边界，报告中明确标为扫描范围，
不将扫描记录数当作已恢复的完整使用项数量。缺失目标或来源冲突均拒绝输出成功结果。
同一来源的重复初始化保留各使用项索引。
