# 场景玩法队伍机关

本批接入 `PlayTeamEntity` 的创建、专用同步、玩家能力归属和结束清理。
它是场景玩法的能力载体，按本轮参与玩家创建，不进入地图格子或普通物体出现列表。
这补齐「未归的熄星」第三章的一项基础依赖；第三章完整玩法仍待接入。

## 行为

- Lua 使用 `SetScenePlayBattlePlayTeamEntityGadgetId(context, group_id, gadget_id)`
  设置本轮机关。组 ID 为 0 时使用当前脚本组；标识必须是整数，拒绝字符串、布尔和非有限数。
- 准备或就绪阶段可设置机关，预备开始时一次创建每名参与者的独立实体。
  配置、能力资源、玩家权限标识和普通队伍必须齐全，否则不会发布部分机关。
  当前能力引擎尚不支持命名的机关 `abilityOverride`，此类配置明确返回失败。
- 使用实体编号类型 12、逻辑实体类型 `PlayTeam`（48），保留本项目的 21 位编号移位。
  机关保存固定场景、玩家对象、UID、权限 peer 和配置编号，使用该玩家的能力管理器。
- 同步通知携带实体、UID、peer、配置及初始 `AbilitySyncStateInfo`。
  创建时先注册并同步全部机关，再初始化服务端配置能力；初始能力状态要求客户端自行初始化。
  场景初始化同步也列出当前机关，不向旁观者额外创建一个机关。
- 能力入口和异步回调识别此类实体。源或目标为机关的客户端回报要求真实归属玩家；
  核对身份与回报处理共用场景锁，已删除机关或他人的机关不能用作回报源／目标。
  机关的 `CurScenePlay` Lua 调用只进入所属轮次，避免其他活动共用玩家时互相影响。
- 胜负结算、中断、房主离场、人数不足、组卸载和场景关闭均清理机关；
  直接挑战仍有足够人数时，仅清理离场者的机关。未通过正式离场通路的失效参与者也由 tick 清理。
- 清理先移除查询入口并失效能力生命周期，随后撤掉机关在其他实体上安装的能力状态，
  保留其他能力的状态，最后发送一次专用删除通知。新轮次生成新实体 ID。
  场景战斗 tick 同时推进机关的能力计时器。

## 7.1 协议核对

客户端文件固定为：

- `YuanShen.exe` SHA-256：
  `7f89938da606c1281659607d464702cddb9a09a7d4320a196630f60a811ec38e`
- `global-metadata.dat` SHA-256：
  `469eccd43aa48fe7a2df4e1caf66fa1268a17f5a4a03fa209e1427e467cb0161`

| 消息 | 原始类型索引／混淆名 | 包号 | 字段 |
| --- | --- | --- | --- |
| SyncScenePlayTeamEntityNotify | 14645 / FNOJJLIIMLA | 25654 | scene 15，列表 4 |
| PlayTeamEntityInfo | 24136 / OPIBOAKIHPJ | 无独立包号 | entity 1，UID 2，peer 3，config 5，ability 6 |
| DelTeamEntityNotify | 40929 / HHDADFOPFFM | 2050 | scene 15，删除列表 11 |
| DelScenePlayTeamEntityNotify | 82052 / HAFBDBHDKHD | 26830 | scene 15，删除列表 3 |

两个删除消息的字段形状相同，语义由实际处理函数与创建路径交叉确认：

1. 从原始元数据还原方法参数类型，定位处理者 `JFGOOBKOBBP`（70066）中的
   `PNHMLIILEKN`（575148）、`PMNIJGGMGJN`（575305）和 `COHFFKJEEHI`（575340），
   分别接收类型 14645、40929 和 82052；没有以类名相似或地址邻近来命名消息。
2. 同步处理函数 `0x1537cdec0` 校验场景，再把子消息的实体／UID／peer／config／ability
   传给 `0x150e7a6a0`。实体不存在时调用创建函数 `0x153d35a00`。
3. 创建函数在 `0x153d35af9` 写入逻辑类型 `0x30`，本地所属机关 ID 在
   `0x153d35c67` 写入 `EntityManager + 0x27c`。
4. 包号 26830 的处理函数 `0x1537e6750` 校验消息的场景，读取并匹配同一 `+0x27c`，
   在 `0x1537e6903` 清零，然后走实体删除路径；这与创建路径互相对应。
5. 包号 2050 的处理函数 `0x1537e29d0` 使用普通队伍的 `+0x25c`，保留本地队伍，
   删除其他队伍实体，走的是另一条流程。

本批修正普通队伍删除通知的包号和字段，新增活动队伍删除 proto／发包器。
从 `data/proto-fanout.json` 移除两种删除消息共用一个候选族的旧配置，发送时使用已确认的独立包号。
原始处理函数、读取器、参数还原脚本、12 处直接机器指令检查和固定哈希在
`debug/aster-mid-20261011/batch79/`。此前第七十七批的未确认记录保留为历史证据。

其余运行类与上一批一致。结果见同目录的 `verification.json`。

`e059ffeac2f42bb774689f165ac3024d4eabe545d98965f86f9ae64d7aaf0866`。
