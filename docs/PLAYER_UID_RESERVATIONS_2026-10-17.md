# 角色 UID 的持久预留与首次建档

## 来源与复现

核对 AstaPS 固定提交 `7cc148d1f752a43d4b9146b3b73f26875902546f`
的 `PlayerUidReservation`、`PlayerUidAllocator` 及 Mongo 预留入口。
本地原来只检查角色文档是否存在，角色尚未保存时，显式请求可以拿到相同 UID，
自动分配还可能占用另一个未建角色账号的指定 UID。

7 项隔离 Mongo 基线检查全部断言失败，错误和跳过为零。
本轮增加持久归属，并保留已有 `PlayerSaveGuard` 的首次插入和版本保护，未改成普通替换保存。

## 已接入的流程

| 记录 | 位置与用途 |
| --- | --- |
| `player_uid_reservations` | 游戏数据库；以 UID 为主键，保存归属 UUID、操作 UUID 及账号／匿名类型，归属 UUID 有唯一索引 |
| `account_uid_owners` | 当时选择的账号数据库；以账号 ID 为主键，保存稳定归属 UUID，UUID 有唯一索引 |

账号身份独立于普通 Account 整份保存。同一数据库中的同一账号会读取同一归属；
不同账号数据库中相同字符串 ID 的账号不能直接接管已有角色。
账号身份记录保留，重置账号计数器也不会让新账号重用删除账号的身份编号。

### 指定 UID 与自动分配

- 新指定 UID 的账号先确认 UID 预留，再确认账号身份和账号插入；不能占用已被角色或另一预留占用的 UID。
- 自动分配保留 `Player` 计数器和 10,000 的起点，并从已有角色的最高有效编号之后开始。
  查询只读取编号，不为计算起点加载整份角色或执行加载回调。
- 跳过控制台、已有角色、其他账号的指定 UID 和持久预留；旧账号指定 UID 已冲突时沿用另选自动编号的行为。
- 同一账号并发预留由唯一归属索引汇合到同一条记录。计数器允许留下空号，不允许回退或回绕。
- 对旧账号及已有角色按需建立归属，沿用已有角色 UID，不替换其进度。
  已有角色与归属冲突、一个账号存在多份角色或记录格式异常时拒绝选择，不另建一份来掩盖冲突。

### 登录与首次建档

`GetPlayerTokenReq` 已使用 `DatabaseHelper.getOrCreatePlayer`：

1. 固定账号与游戏 Datastore，取得带归属和操作 UUID 的预留。
2. 已有匹配角色时加载原档；否则才调用原 `PlayerCreationEvent` 选择的角色构造器。
3. 确认新角色账号与预留一致，使用原 PlayerSaveGuard 确认首次插入。
4. 同账号另一首登已经插入，或本次插入实际成功但确认丢失时，冷读已保存的同 UID、同账号角色。
5. 构造或写入失败但尚未建档时保留预留，下次登录继续使用该 UID。

预留对象固定两份 Datastore，运行模式／连接切换不会中途改变保存目标。
保存前仍核对持久归属和账号存在状态，裸 UID 不是账号归属凭证。

## 插件入口与数据维护

账号角色创建应使用 `DatabaseHelper.getOrCreatePlayer(account, playerClass, factory)`，
或 `PlayerUidAllocator.reserve` 与 `createOrLoad` 传递同一个预留对象。
旧 `getNextPlayerId(int)` 保留为持久匿名分配；随后只传整数给 `generatePlayerUid` 不会接管已占用的预留，
可能另选编号。本地登录已迁移到账号入口。

备份与迁移应包含上述两份集合，并保持账号数据库与游戏数据库的对应关系。
这些记录不自动过期或释放；账号插入确认不明时，指定 UID 可能保留为待核对预留。
没有加入自动删除旧归属或释放孤立 UID 的功能，避免晚到写入把编号交给不同账号。

## 保留的边界

并发测试使用同进程的多个数据库句柄和真实 Mongo 写入，不代表真实多服务故障切换、
账号删除与登录接管的完整时序、任意插件绕过入口写入或网络主从切换已经验收。
两份数据库之间未增加分布式事务；失败时允许保留身份／预留和编号空缺，不能按数量或当前空档猜测可回收性。
普通 Account 后续更新的版本保护、孤立预留的审计处理与完整客户端登录仍需继续核对。
所有写入实例应使用新预留入口；混用旧分配或原始写库无法得到本项归属保证。
原有认证策略、协议、资源和奖励未改动，用户此前反馈的游戏错误尚未实机复验。
