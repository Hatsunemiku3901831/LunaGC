## 原生字段与回调

二进制与 metadata 使用[提取工具](../tools/extract_client_type_names.py)相同的 SHA-256 配置。
`EOHNDJFNKOK.ENAAGIDHLHK`，地址 `0x14a24c5c0`，组装调用参数 31 的实际消息：

| 现有消息／字段 | 本次确认的含义 |
| --- | --- |
| `TpsWeaponAccessoryInfo.ammunition_type`，7 | 弹药槽位，对应 combat 配置的 `FDEMCPFAFOC` |
| `ammunition_config_id`，11 | 弹药池，对应 `OGBGNCBLEEI` |
| 原 `KAPHEDKKFGK`，12 | 关联对象的实体编号，由对象的 `0x3a8` 字段写入 |
| 原 `MHFBBNKOBPK`，14 | 该槽位当前弹匣数量，由运行状态的 `0xa0` 字段写入 |

消息的历史名称保持不变；字段 12／14 改用 `entity_id`／`current_ammunition`，wire 编号不变。
这些条目用于弹匣状态，不据此增加配件或解锁配件。

普通费用入口 `0x14a24ac70` 向该发送函数传入 Cost 及负费用。
换弹入口 `0x14a24c290` 更新当前弹匣后，在 `0x14a24c43c` 至 `0x14a24c451`
传入 Reload、总量变化 0，再跳到同一发送函数。
换弹是在弹药池内部装填，不增加或扣除弹药总量。

原生初始化 `0x14a24b800` 优先消费已提供的槽位快照，否则使用当前 combat 配置的初始值；
原生储备计算继续从总量减去当前弹匣数量。

## 服务端处理

- 玩家新增 `tpsMagazineAmmunition`，按槽位保存观察到的数量，明确的 0 也会保存。
- Cost 同时应用合法总量费用与弹匣快照；Reload 只更新弹匣，拒绝非零总量变化。
- 全批校验通过后才改变状态，成功时总量与弹匣合并为一次玩家保存；相同 Reload 快照不重复保存。
- 快照实体必须对应当前角色实际穿戴、仍在当前场景登记的武器；槽位与弹药池必须匹配资源。
- 拒绝未知／旧实体、错误槽位与池、无符号越界、重复槽位、Cost 增加已知弹匣及共享池超额预留。
- 多条快照中任何一条无效，会拒绝整个调用，包括其中的总量费用。

场景武器消息恢复已知弹匣，不再把共享总量填入每个弹匣。
未知弹匣省略槽位条目，让客户端按当前资源初始化；不写死 45／75 等容量。
明确的零值仍作为条目发送，避免重新进入场景时被当成未知弹匣初始化。

恢复视图只为当前队伍及正在序列化的武器预留弹药，未穿戴武器的旧记录不占当前池。
损坏的超额记录按槽位编号顺序限制在共享总量内，读取过程不修改或保存原存档。
删除武器会清除对应的弹匣记录，弹药总量保持不变；场景迁移保留已观察到的记录。

进场初始化在 `PlayerEnterSceneInfoNotify` 前发送完整总量，换装通知也先发送总量。
当前角色没有 TPS 武器、但队伍其他角色有时，同样初始化总量。
遍历队伍使用现有快照接口，避免切队中断本次读取。
这些检查证明服务端发送顺序；客户端实际接收与画面仍需实机验收。

## 验证

先新增协议与存档结构、行为回归测试，旧处理在 14 项检查中失败：
弹匣被写成总量、射击快照不保存、Reload 状态遗漏、错误快照被接受及删除后记录残留。

新增 **21 项测试**，包含：

- 原生字段的独立字节向量、Cost／Reload、明确零值及幂等 Reload。
- 关联武器、槽位、池、整数边界、共享预留及整批拒绝。
- 未知弹匣、已保存弹匣、未穿戴记录、只读限幅和武器删除。
- 真实进场处理器的发送顺序、换装顺序、非当前角色的 TPS 武器及切队读取。
- 扩展现有真实 Mongo 测试，核对零值／非零值往返、旧字段缺失与只读时不写回。

两项原有路由用例误用 Reload 表达负费用，已改为原生 Cost；路由与 `localId` 检查保留。
