# Compose 模式下的客户端补丁自动恢复

## 行为

- `task serve` / `task runtime` 完成镜像构建并等待服务健康后，检查本机客户端补丁，启动独立的 Windows 后台守护。
- 守护在启动命令、终端和 Codex 会话结束后继续运行。按客户端路径去重，重复启动不会增加监控进程。
- 再次启动时核对监控脚本摘要；脚本更新后协作停止旧监控并加载新版，不影响游戏进程。
- 游戏运行时不修改 DLL。游戏退出或补丁文件发生变化后检查；发现原版启动文件、旧补丁、缺失代理或 `.lunagc-live` 残留时重新安装，并再次验证。
- 失败会记录状态和日志，并退避重试；不会将安装失败或复验失败显示为成功。
- 常态轮询只比较文件元数据，不反复读取完整 DLL；日志有大小限制。
- 目录解析优先使用进程环境中的 `GAME_PATH`，其次 `.env.local`、`.env`，最后启动器注册表。直接运行 PowerShell 脚本也能读取项目配置。
- 没有客户端的服务器跳过监控；显式配置了错误路径时报告错误。

## 管理入口

| 入口 | 作用 |
| --- | --- |
| `task patch:check` | 单次检查并修复；游戏运行中暂缓修改 |
| `task patch:guard` | 检查补丁并启动或复用后台监控 |
| `task patch:guard:status` | 查看心跳、最近结果和进程信息 |
| `task patch:guard:stop` | 协作停止监控，保留游戏与 Compose 服务 |
| `task patch:reset` | 先停止监控，再恢复原版客户端 |

状态和日志位于忽略目录 `debug/client-patch/<客户端路径摘要>/`。
`LUNAGC_CLIENT_PATCH_GUARD=0` 跳过 Task 启动服务时的监控步骤，不停止已有守护。
Windows 重启或注销后，重新执行 `task serve` 或 `task patch:guard` 启动宿主机监控。
直接执行 Docker Compose 只管理容器，需要另行启动客户端守护。

## 安装器保护

- apply/reset 按客户端路径共用修改锁，拿到锁后再次检查游戏进程。
- 状态检查包括安装文件与当前 `ext.dll` 的 SHA256、原版代理文件及带 PID 的残留。
- 客户端更新后，原版备份按当前文件刷新；旧原版按 SHA256 归档保留。
- 旧开发监控器恢复时，在锁内重新检查残留。若显式 reset 或其他恢复已处理，则跳过，防止重新安装已移除的补丁。

- 目录解析和配置优先级：5 项通过。
- 补丁安装、复验、备份、进程保护、锁竞争及延迟恢复：10 项通过。
- 守护进程的独立存活、去重、模拟异常退出恢复、失败重试、脚本升级、PowerShell 5/7 心跳及状态传播：14 项通过。

共 39 项相关测试通过；修复前失败记录与通过记录均保留在 `debug/`。

本机已通过 `task serve` 启用守护，并在启动命令结束后单独确认进程仍存活、状态为 `ready`，重复启动保持同一实例。Compose 已构建并更新，运行容器使用本次构建的镜像；游戏服务和 MongoDB 健康，GM 返回 HTTP 200，MongoDB 容器未替换。

## 部署时发现的独立服务端问题

部署前原服务的健康检查为 HTTP 503，JVM 报告 2 条死锁线程：玩家 tick 持有 Player 锁等待队伍列表，场景切换移除角色时持有队伍列表锁，能力回调反向等待 Player 锁。
当时已保存线程栈并重建游戏服务恢复健康，未修改 MongoDB 或删除持久化卷。客户端守护改动没有修复该 Java 锁顺序问题，重启恢复不能视为根因已解决。

后续已通过独立回归测试修复该锁循环，并覆盖试用队伍的同类清理路径，见[场景切换死锁修复](SCENE_TRANSFER_DEADLOCK_2026-10-18.md)。

本机验证和诊断记录保留在忽略目录 `debug/compose-patch-*.log` / `debug/compose-patch-*.json`，包括部署前健康结果和线程栈。
